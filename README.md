# 章节加载失败归因：不是缓存不够，是目录同步的长尾太长了

分析对象：`data/chapter_requests.csv`（1040 条章节请求，2026-09-01 ~ 09-07）。
所有数字均由 `analysis/` 下脚本从该文件算出，命令见文末「复现」。

---

## 一、我的判断

### 1. 看到了什么

先把口径摆清楚，后面所有比率都基于这个分母：

| 项 | 数值 |
|---|---|
| 总请求 | 1040 |
| `load_status` 有回传 | 995（95.7%） |
| 其中失败（`0`） | 101 |
| 失败率（以有回传为分母） | **10.15%** |
| `load_status` 为空（未回传） | 45（4.33%） |

**时区陷阱**：`req_time` 带 `+08:00`，`catalog_synced_at` 带 `Z`。直接相减会把同步滞后多算 8 小时，整份结论会全错。脚本统一转成 UTC 后再算 `lag_min`。

### 2. 关键发现：滞后 20 分钟是一条断崖

把 `catalog_synced_at` 与 `req_time` 的差定义为 `lag_min`（请求发生时，边缘节点目录已经陈旧了多少分钟）：

| 同步滞后 | 请求数 | 失败数 | 失败率 |
|---|---|---|---|
| ≤ 20 分钟 | 712 | 25 | **3.51%** |
| > 20 分钟 | 283 | 76 | **26.86%** |

风险比 **RR = 7.6 倍**。并且 **75.2%（76/101）的失败请求落在 >20 分钟这一侧**，而这一侧只占 28.4% 的流量——失败高度集中在少数陈旧请求上。

拐点不是切区间切出来的：滞后在 **[20, 22) 区间没有任何样本**（0 条），而 `[18,20)` 失败率 2.5%、`[22,24)` 直接跳到 36.4%。也就是说数据里存在一条清晰的分界，20 分钟前是正常运行态，20 分钟后进入失效态。

### 3. 反直觉的部分：缓存 TTL 不是主因

单看 `cache_ttl_sec` 确实有梯度（0–5 秒档失败率 15.3%，11–20 秒档 7.0%），看起来像“缓存过期导致失败”。但**控制滞后后就塌了**：

| 层 | TTL 低半区 | TTL 高半区 |
|---|---|---|
| 滞后 ≤ 20 | 5.1% | 1.8% |
| 滞后 > 20 | **25.3%** | **28.5%** |

在真正出问题的高滞后层里，TTL 高低几乎没有任何区分度（25.3% vs 28.5%），甚至方向相反。**TTL 是滞后带来的伴生现象，不是原因**——目录陈旧时，即使缓存还有 25 秒有效期，请求照样失败（高滞后+高 TTL 组失败率 28.5%）。

同样，品类的差异（轻小说 17.4% vs 都市生活 5.4%）在控制滞后后也基本抹平（高滞后层里各品类都在 15.8%–35.1%），是流量结构差异，不是内容问题。

### 4. 根问题

**目录同步的“最坏情况”没有被约束住。**

同步的平均节拍看着不差（各节点相邻同步间隔中位数 20–28 分钟），但长尾很长：滞后最大值到 70 分钟，>20 分钟的陈旧请求占了 28.4% 的流量。系统对“平均情况”是健康的，对“长尾”是失效的——而失败恰恰几乎全部由长尾贡献。

一句话：**不是同步频率整体不够，是同步的长尾没有被兜住**。任何一次同步窗口被拉长到 20 分钟以上，这段窗口内的读者请求就进入 26.9% 的失败区间。

## 二、根因的边缘疑点（已标注，未定论）

按区域分层后出现一个反常现象，我认为需要单独排查，**不把它混进主结论**：

| 区域 | 滞后 ≤ 20 失败率 | 滞后 > 20 失败率 |
|---|---|---|
| 华东节点 | 9.0%（13/144） | **1.6%（1/61）** |
| 华北节点 | 0.7%（1/136） | 32.8%（19/58） |
| 华南节点 | 3.2%（5/156） | 25.5%（14/55） |
| 海外节点 | 2.3%（3/128） | 38.0%（19/50） |
| 西南节点 | 2.0%（3/148） | 39.0%（23/59） |

华东节点的表现与其他四区完全相反：目录新鲜时反而有 9.0% 失败，目录陈旧时几乎不失败。样本量下（13 次失败）不足以定论，最可能是存在**另一条独立故障路径**（例如该节点本地缓存的驱逐策略或回源路径异常），需要拉该节点的缓存命中与回源日志才能确认。主结论不依赖它。

## 三、做了什么

1. **建立可复现的分析管线**（`analysis/`，三个脚本，纯 pandas，无外部数据）。
2. **定位机制**：用滞后分层 + 控制变量，排除了缓存 TTL、品类、区域作为主因。
3. **给出可执行的策略**：把每个节点的目录同步滞后压到 ≤ 20 分钟（触发式补同步，而不是整体提高频率），并按题目口径算了投入产出。

## 四、怎么证明有用

题目口径：每次失败损失 75 分钟，每提前触发一次目录同步花费 12 分钟。

**当前损失**：101 次失败 × 75 = **7575 分钟**。

**策略**：对滞后将要超过 20 分钟的节点提前触发一次同步。

悲观计费（每个高风险请求各算一次同步，不考虑合并——这是成本上界）：

| 项 | 数值 |
|---|---|
| 高风险请求（滞后>20） | 283 |
| 其中失败 | 76 |
| 避免损失 | 76 × 75 = 5700 分钟 |
| 同步成本 | 283 × 12 = 3396 分钟 |
| **净收益** | **+2304 分钟** |
| 投入产出比 | **1.7 : 1** |

乐观计费（按“陈旧同步版本”合并，269 个版本）：成本 3228 分钟，净收益 +2472 分钟。

**策略执行后残余损失**：滞后 ≤20 的流量仍有 25 次失败 → 1875 分钟，相对当前 7575 分钟**下降 75.2%**。

即便采用最不利的口径（把 45 条未回传全部计为失败），失败数 146 次、损失 10950 分钟，滞后分层的结论不变，策略收益只会更大。

> 需要强调：这是**观测数据的相关性 + 时序方向**推出的因果（同步发生在请求之前，滞后是请求时的既成状态），不是随机对照实验。上线验证方式见下。

## 五、上线后怎么验证（下一步）

- 灰度：选 2 个节点把同步间隔上限压到 20 分钟，与其余 3 个节点同期对照，比较 `load_status` 失败率。按当前数据，预期失败率从 ~10% 降到 ~3.5%。
- 监控指标：`lag_min > 20` 的请求占比（当前 28.4%）应降到接近 0；这是比失败率更早、更灵敏的预警指标。

## 六、局限

- 45 条 `load_status` 为空（4.3%）无法判定，主口径排除，敏感性分析已给上限。
- 成本系数（75 / 12 分钟）直接采用题目口径，未做独立校验。
- 华东节点异常未定论，见第二节。
- 数据仅 7 天、5 节点，未覆盖大促等流量峰值场景。
