# 章节加载失败归因：两条独立的失效路径，不是缓存整体不够

分析对象：`data/chapter_requests.csv`（1040 行，2026-09-01 ~ 09-07，5 个区域节点）。
所有数字都由 `analysis/` 下脚本从该文件算出，命令见文末「复现」。

**结论先行**：失败不是一个原因造成的，而是两条独立路径的叠加——
① 四个节点的**目录同步滞后超过 20 分钟**（失败率 27.9%）；
② **华东节点的缓存剩余 TTL ≤ 5 秒**（失败率 32.4%，与目录是否陈旧无关）。
缓存 TTL 对另外四个节点几乎无影响，目录滞后对华东节点几乎无影响。分开治理，残余损失可降 86%。

## 一、我的判断

### 1. 先清口径：数据里有两个坑

**坑一：50 组重复行。** `request_id` 定义为“全局唯一业务编号”，但 1040 行里只有 **990 个唯一 ID**，50 组完全重复（每个字段都一样）。这是导出侧重复，会让分母虚增。**主口径按 `request_id` 去重**，原始口径作为敏感性对照。

**坑二：时区不一致。** `req_time` 带 `+08:00`，`catalog_synced_at` 带 `Z`。直接相减会把同步滞后凭空多算 8 小时，所有分档全错。脚本统一转 UTC 后再做差。

去重后的口径：

| 项 | 数值 |
|---|---|
| 唯一请求 | 990 |
| `load_status` 有回传 | 948（95.8%） |
| 其中失败（`0`） | 99 |
| 失败率（以有回传为分母） | **10.44%** |
| `load_status` 为空（未回传） | 42（4.24%） |

### 2. 两条路径的分工（核心表）

把请求按「目录是否陈旧（滞后 >20 分钟）」×「缓存是否临期（TTL ≤5 秒）」×「区域」切开后，结构非常干净：

| 区域 | 滞后>20, TTL>5 | 滞后>20, TTL≤5 | 滞后≤20, TTL≤5 | 滞后≤20, TTL>5 |
|---|---|---|---|---|
| 华东节点 | **0.0%** (n=51) | 10.0% (n=10) | **41.7%** (n=24) | 1.8% (n=112) |
| 华北节点 | 39.1% (n=46) | 0.0% (n=7) | 4.3% (n=23) | 0.0% (n=108) |
| 华南节点 | 25.0% (n=40) | 33.3% (n=12) | 4.3% (n=23) | 3.1% (n=128) |
| 海外节点 | 44.7% (n=38) | 20.0% (n=10) | 9.1% (n=22) | 1.0% (n=98) |
| 西南节点 | 40.4% (n=47) | 50.0% (n=8) | 0.0% (n=24) | 2.6% (n=117) |

读法：
- **华东那一行，看 TTL 列**：TTL ≤5 时 41.7%，TTL >5 时 1.8%——即使目录陈旧 51 分钟以上，失败率也是 **0.0%**。
- **其他四行，看滞后列**：滞后 >20 一律 25%–45%，滞后 ≤20 时 0%–4.3%——TTL 高低几乎不起作用。

### 3. 路径一：目录同步滞后 20 分钟是一道断崖

| 同步滞后 | 请求数 | 失败率 |
|---|---|---|
| ≤ 20 分钟 | 679 | **3.53%** |
| > 20 分钟 | 269 | **27.88%** |

风险比 **RR = 7.9 倍**；**75.8%（75/99）的失败来自只占 28.4% 流量的高滞后请求**。

拐点不是切区间切出来的：滞后在 **[20, 22) 区间样本数为 0**（去重前后都是），`[18,20)` 失败率 2.6%，`[22,24)` 跳到 40.0%。非华东节点按滞后细分：0–10 分钟 2.9%、10–20 分钟 1.5%、20–25 分钟 **50.0%**、25 分钟以上 28%–38%。20 分钟前是正常运行态，之后直接进入失效态。

### 4. 路径二：华东节点的缓存剩余 TTL 5 秒断崖

| 华东节点 TTL | 请求数 | 失败率 |
|---|---|---|
| 0–2 秒 | 8 | **50.0%** |
| 2–5 秒 | 21 | **33.3%** |
| 5–6 秒 | 5 | 0.0% |
| 6–10 秒 | 22 | 4.5% |
| 10–20 秒 | 77 | 1.3% |
| 21–30 秒 | 64 | **0.0%** |

整体：TTL ≤5 秒 **32.4%（11/34）**，TTL >5 秒 **1.2%（2/163）**，风险比 **27 倍**。切点同样不是人为划的，5 秒两侧直接断开。

**关键对照**：同样的「滞后 ≤20 且 TTL ≤5」条件，其他四个节点合计只有 **4.3%**（4/95）。所以这不是“全局缓存策略问题”，是华东节点自己的问题。

### 5. 被排除的假线索

- **缓存 TTL 是全局主因？** 否。单看全样本 TTL ≤5 秒档失败率 15.3%，看着像主因；但那是被华东和滞后混杂出来的。对四区而言，滞后 ≤20 时 TTL ≤5 的失败率只有 4.3%。
- **品类？** 否。轻小说 17.4% vs 都市生活 5.4%，但高滞后层各品类都在 16%–35%，差异是流量结构造成的。
- **区域整体不行？** 否。华东总失败率 6.8% 反而是五区最低，但它有自己特有的失效条件；只看总失败率会完全看反。

### 6. 根问题

**两个不同的兜底机制同时缺失。**

- 四区：**目录同步只保证“平均节拍”健康（相邻同步间隔中位数 20–28 分钟），没保证“最坏情况”**。长尾一拉到 20 分钟以上，该窗口的读者请求就进入约 28% 的失败率。这与缓存无关——目录陈旧时缓存还剩多久都不重要。
- 华东：**缓存临期（TTL ≤5 秒）时没有可用的回源兜底**，而该节点的目录同步反而做得很好（滞后 >20 且 TTL 正常的 51 条请求，零失败）。说明它把资源压在了目录同步上，缓存层缺了兜底。

一句话：**四区要补“目录同步长尾”，华东要补“缓存临期回源”。把它们当成同一个“缓存问题”去调，两边都调不对。**

## 二、做了什么

1. 建立可复现管线（`analysis/`，6 个脚本，纯 pandas）。
2. 清理数据口径：识别 50 组重复行、对齐时区，给出主口径与敏感性对照。
3. 用「滞后 × TTL × 区域」交叉加控制变量，把两个机制拆开，并排除了 TTL 全局假因、品类、区域总失败率三种误判。
4. 按题目口径算出两条策略各自的收益，给出可落地的监控阈值。

## 三、怎么证明有用

题目口径：每次失败损失 **75 分钟**，每提前触发一次目录同步花费 **12 分钟**。

**当前损失**：99 次失败 × 75 = **7425 分钟**。

### 策略 A：四区目录滞后兜底（滞后上限 20 分钟）

| 项 | 数值 |
|---|---|
| 高风险请求（四区，滞后>20） | 208 |
| 其中失败 | 74 |
| 避免损失 | 74 × 75 = 5550 分钟 |
| 同步成本（上界：每请求单算一次同步） | 208 × 12 = 2496 分钟 |
| **净收益** | **+3054 分钟** |
| 投入产出比 | **2.2 : 1** |

成本按最悲观方式计（不合并同一节点的连续请求，实际成本只会更低），收益仍为正。

### 策略 B：华东缓存临期预热（TTL 下限 5 秒）

| 项 | 数值 |
|---|---|
| 高风险请求（华东，TTL≤5） | 34 |
| 其中失败 | 11 |
| 避免损失 | 11 × 75 = **825 分钟** |

预热成本题目未给口径，**此处不做净收益断言**，只给收益上限。但这类请求只占华东流量的 17%（34/197），预热是小范围动作，成本很可能远低于 825 分钟。

### 两条一起做

| 指标 | 当前 | 两条都做之后 |
|---|---|---|
| 失败次数 | 99 | 14 |
| 损失（分钟） | 7425 | **1050** |
| 降幅 | — | **−85.9%** |

### 敏感性（结论不随口径翻转）

| 口径 | 失败数 | 损失 |
|---|---|---|
| 主口径（去重，NULL 排除） | 99 | 7425 分钟 |
| 不去重（原始 1040 行） | 101 | 7575 分钟 |
| NULL 全部计为失败（最不利） | 141 | 10575 分钟 |

三种口径下，滞后断崖（RR 7.9）与华东 TTL 断崖（RR 27）都成立，策略方向不变。

> 因果性说明：这是观测数据。滞后与 TTL 都是请求发生时的既成状态（同步事件在请求之前），时序方向支持“状态导致失败”；但不是随机对照实验，上线验证方式见下。

## 四、上线怎么验证

**灰度**：华东先做缓存预热（TTL <5 秒触发），其他四区先做同步兜底（滞后逼近 18 分钟时触发补同步，留 2 分钟缓冲），保留一个节点不动作对照。

**预期**：四区失败率从 35.6% 降到 ~2%；华东从 32.4%（TTL≤5 部分）降到 ~1%。

**监控指标（比失败率更早预警）**：
- 四区：`lag_min > 20` 的请求占比（当前 28.4%）→ 目标趋近 0
- 华东：`cache_ttl_sec ≤ 5` 的请求占比与命中率

## 五、局限

- 42 条 `load_status` 为空（4.24%）无法判定，主口径排除，敏感性已给最不利上限。
- 成本系数（75 / 12 分钟）直接采用题目口径，未独立校验；华东预热的成本没有口径，未做净收益断言。
- 华东 TTL 路径的**机制**（是回源超时、还是缓存驱逐策略、还是预热缺失）无法从这份日志区分，需要该节点的缓存命中/回源日志。本文只到“什么条件下会失败”为止。
- 数据仅 7 天、5 节点，未覆盖大促等峰值场景；门槛（20 分钟 / 5 秒）在大促期间可能漂移，需上线后重新校准。
