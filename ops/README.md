# 监控与取证：把 README 的结论变成能上线的东西

本目录是**落地物**，不参与结论推导。结论与数字全部在根目录 `README.md`，由 `analysis/` 脚本产出。

---

## 一、日志字段 → 指标映射

`alerts.yml` 里的指标名是占位符。按这张表把离线日志接到指标系统：

| 指标 | 标签（从日志列来） | 取值 |
|---|---|---|
| `chapter_requests_total` | `region`（5 个节点） | 请求计数 |
| 同上 | `load_status` | `0` / `1` / 不回传（不计入） |
| 同上 | `catalog_lag_bucket` | `le20` / `gt20`（滞后 = `req_time - catalog_synced_at`，**两边都必须先转 UTC**） |
| 同上 | `cache_ttl_bucket` | `le5` / `gt5` |

两个必须写对的点：

1. **时区**：`req_time` 是 `+08:00`，`catalog_synced_at` 是 `Z`。在采集端不做统一，滞后会多算 8 小时，`gt20` 这个桶会把全部流量吞进去。
2. **分母**：`load_status` 为空的行不参与失败率。按 `0|1` 过滤，不要用总请求数。

## 二、阈值与依据

| 告警 | 阈值 | 依据（README 第三节实测） |
|---|---|---|
| 失败率 | > 5%，持续 10 分钟 | 正常态 3.5%（滞后≤20）、失效态 27.9%（滞后>20） |
| 目录陈旧占比 | > 3%，持续 10 分钟 | 当前 28.4%，目标趋近 0；陈旧请求贡献 75.8% 的失败 |
| 华东临期占比 | > 5%，持续 10 分钟 | 华东 TTL≤5 占 17% 流量，该区间失败率 32.4% |

阈值不是拍的：每条都在“正常态”和“失效态”之间取，且离两侧都有余量。上线后如基线漂移（大促、版本变更），用 `analysis/07_peak_drift.py` 的方法重新校准。

## 三、Runbook

<a id="runbook-stale"></a>
### A. `CatalogStalenessShareHigh`（目录同步长尾）

这是**主要**故障路径，优先处理。

1. 看该节点目录同步任务：最近一次成功时间、队列积压、单次耗时。滞后 >20 分钟说明有一次同步被拖长或漏掉。
2. 判断是“慢”还是“断”：同步间隔中位数若仍正常（20–28 分钟）但长尾变长，是慢；若间隔整体拉长，是任务失败或调度堆积。
3. 临时止血：手动触发一次全量同步（成本约 12 分钟/次，按题目口径）。
4. 长期：把同步间隔上限压到 20 分钟以内，18 分钟触发补同步留 2 分钟缓冲。

<a id="runbook-ttl"></a>
### B. `EastCacheTtlLowShareHigh`（华东缓存临期）

**只对华东节点有意义**。其他节点同样条件下失败率仅 4.3%，不要照搬。

1. 先确认不是全局缓存问题：对比其他四区同指标，若只有华东高，走第 2 步。
2. 查华东的**近过期回源/刷新**路径：回源错误码分布、刷新耗时 P99、上游返回状态。
3. 临时止血：对该节点 TTL <10 秒的章节做主动预热。
4. 长期：定位是回源超时、上游限流，还是刷新任务缺失。

<a id="runbook-failure"></a>
### C. `ChapterLoadFailureRateHigh`（失败率）

先看是 A 还是 B 触发：

- 同时触发 A → 按 A 处理（目录长尾）。
- 只触发 B 且 `region=华东节点` → 按 B 处理。
- 都不触发但失败率仍高 → **不在本分析的覆盖范围内**，属新故障模式，按常规排查（上游 5xx、超时、客户端异常）。

## 四、华东机制取证清单

现有数据只能证明“什么条件下失败”，无法区分内部机制。已用数据排除两条：

| 假设 | 检验方法 | 结果 |
|---|---|---|
| H1 回源耗时随正文变长而超时 | 华东 TTL≤5 组内看 `chapter_words` | **不支持**：失败组均值 52.9 字、成功组 54.5 字；>60 字档失败率反而最低（11.1%） |
| H2 华东缓存驱逐更激进（TTL 被压得更低） | 对比各区域 TTL 分布 | **不支持**：五区 TTL 均值 14.7–16.0、中位数 14–18，无差异 |
| H3 近过期时的刷新/回源路径本身失败 | 需要新日志，见下 | 待验证（当前唯一未被排除的假设） |

要把 H3 钉死，需要这些日志（当前数据集里没有，**不得凭猜测下结论**）：

1. **回源请求日志**：章节 ID、回源时间、上游返回码、耗时、重试次数（按节点）。
2. **缓存命中日志**：命中/未命中/已过期三种状态，以及过期后的刷新结果。
3. **刷新任务日志**：华东节点的缓存预热/刷新任务成功率与失败原因。
4. **上游节点维度**：华东回源指向的源站/中心节点是否与其他区不同。

拿到 1 和 2 就能直接判定：若失败集中在“已过期→触发刷新→刷新失败”，即 H3 成立，修的是回源链路；若失败集中在“未命中且回源超时”，则是上游容量问题。
